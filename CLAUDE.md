# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## General

- Follow clean code principles.
- Use SOLID where appropriate.
- Avoid unnecessary abstractions.
- Do not overengineer.
- Prefer simple and maintainable solutions.

## Task Scope

- Focus only on files directly relevant to the current task.
- Do not scan the entire repository unless explicitly requested or necessary.
- Do not read unrelated files.
- Avoid repeatedly inspecting files already understood.
- Prefer targeted searches over broad searches.
- Reuse information already available in the current context.
- Do not perform unnecessary tool calls.
- Prioritize the current conversation context over rediscovering already known information.
- If the required information is already available, do not inspect it again.

## Architecture

- Follow the existing project architecture.
- Do not introduce new design patterns without justification.
- Keep classes focused on one responsibility.
- Minimize dependencies between modules.

## Coding

- Before modifying code, inspect only the relevant files.
- Change only files necessary for the task.
- Do not rewrite working code unnecessarily.
- Do not add libraries without approval.
- Do not make unrelated improvements or refactoring.
- Follow existing naming and formatting conventions.

## Workflow

- For straightforward tasks, proceed directly without creating a plan.
- For complex tasks, create a short implementation plan first.
- Implement one logical task at a time.
- Prefer minimal changes.
- Follow TDD when changing behavior:
  1. Write or update the test.
  2. Run it and confirm it fails for the expected reason.
  3. Implement the minimal change.
  4. Run the test again and confirm it passes.
- If a test cannot reasonably be written for the task, explain why before skipping TDD.
- Run only relevant tests.
- Do not run the full test suite unless necessary or requested.
- Report modified files and test results.
- Never claim tests passed if they were not executed.
- Stop when the requested task is completed.

## Communication

- Explain important architectural decisions.
- Keep routine responses concise.
- Ask before making breaking architectural changes.
- Explain code in beginner-friendly language when requested.
- Do not overwhelm with unnecessary explanations or alternatives.

## Commands

Unity editor binary:

`/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity`

Batch-mode commands fail if the project is already open in the Editor — close it first or run tests from the Editor's Test Runner window.

Run EditMode tests:

```sh
UNITY=/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity

$UNITY -batchmode -nographics -projectPath . -runTests -testPlatform EditMode \
  -testResults Temp/editmode-results.xml -logFile -
```

Run a single test / fixture:

```sh
$UNITY -batchmode -nographics -projectPath . -runTests -testPlatform EditMode \
  -testFilter "WaterChaos.Tests.SomeFixture.SomeTest" \
  -testResults Temp/results.xml -logFile -
```

The `.csproj` / `.slnx` files are generated by Unity. Do not edit them; change `.asmdef` files instead.

Compiler errors show up in `Logs/` or the Editor console, not via `dotnet build`.

## Code Layout and Assemblies

- `Assets/WaterChaos/Scripts/` → assembly `WaterChaos.Runtime` (root namespace `WaterChaos`, no references).
- Gameplay/domain code such as `Water/Data/WaterFlowData.cs` lives here.
- Folder paths mirror namespaces (`Water/` → `WaterChaos.Water`).
- `Assets/WaterChaos/Tests/EditMode/` → `WaterChaos.Tests.EditMode` (NUnit, Editor-only, references `WaterChaos.Runtime`).
- Tests can only access code in `WaterChaos.Runtime`.
- `Assets/Scripts/Player/` (`PlayerMovement`, `PlayerLook`) has no asmdef and compiles into `Assembly-CSharp`, despite using namespace `WaterChaos.Player`.
- `WaterChaos.Runtime` currently has no reference to `Unity.InputSystem`; moving input-reading scripts into it requires adding that reference.
- `Assets/TutorialInfo/` and `Assets/Readme.asset` are URP template leftovers.

## Conventions

- C# language version is **9.0** (Unity compiler).
- Do not use primary constructors, file-scoped namespaces, `required`, raw string literals, etc.
- Private serialized fields use `_camelCase` with `[SerializeField] private`.
- Group serialized fields with `[Header(...)]`.
- Player scripts read devices directly (`Keyboard.current`, `Mouse.current`) and null-check them in `Update`.
- The `InputSystem_Actions.inputactions` asset exists but is not yet wired up.
- Data types such as `WaterFlowData` are immutable `readonly struct`s.
- Data types validate values in constructors.
- Document units in XML comments where applicable.
