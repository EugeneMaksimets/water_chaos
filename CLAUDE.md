# Project Instructions

## General
- Follow clean code principles.
- Use SOLID where appropriate.
- Avoid unnecessary abstractions.
- Do not overengineer.
- Prefer simple and maintainable solutions.

## Architecture
- Follow the existing project architecture.
- Do not introduce new design patterns without justification.
- Keep classes focused on one responsibility.
- Minimize dependencies between modules.

## Coding

- Run relevant tests after changes.

## Communication

## Project

Water Chaos — a Unity 6 (editor `6000.6.7f1`) first-person game using URP (17.6) and the **new Input System only** (`activeInputHandler: 1`; the legacy `UnityEngine.Input` API will throw). Main scene: `Assets/Scenes/SampleScene.unity`.

## Commands

Unity editor binary: `/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity`. Batch-mode commands fail if the project is already open in the Editor — close it first or run tests from the Editor's Test Runner window.

```sh
UNITY=/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity

# Run EditMode tests (results written as NUnit XML)
$UNITY -batchmode -nographics -projectPath . -runTests -testPlatform EditMode \
  -testResults Temp/editmode-results.xml -logFile -

# Run a single test / fixture (fully-qualified name or regex)
$UNITY -batchmode -nographics -projectPath . -runTests -testPlatform EditMode \
  -testFilter "WaterChaos.Tests.SomeFixture.SomeTest" -testResults Temp/results.xml -logFile -
```

The `.csproj`/`.slnx` files are generated by Unity — don't edit them; change `.asmdef` files instead. Compiler errors show up in `Logs/` / the Editor console, not via `dotnet build`.

## Code layout and assemblies

- `Assets/WaterChaos/Scripts/` → assembly **`WaterChaos.Runtime`** (root namespace `WaterChaos`, no references). Gameplay/domain code such as `Water/Data/WaterFlowData.cs` lives here. Folder path mirrors namespace (`Water/` → `WaterChaos.Water`).
- `Assets/WaterChaos/Tests/EditMode/` → **`WaterChaos.Tests.EditMode`** (NUnit, Editor-only, references `WaterChaos.Runtime`). Tests can only see code in `WaterChaos.Runtime`.
- `Assets/Scripts/Player/` (`PlayerMovement`, `PlayerLook`) has **no asmdef**, so it compiles into the default `Assembly-CSharp` even though it uses namespace `WaterChaos.Player`. It is therefore not reachable from the test assembly. `WaterChaos.Runtime` also has no reference to `Unity.InputSystem`, so moving input-reading scripts into it requires adding that reference.
- `Assets/TutorialInfo/`, `Assets/Readme.asset` are URP template leftovers.

## Conventions

- C# language version is **9.0** (Unity's compiler): no primary constructors, file-scoped namespaces, `required`, raw string literals, etc.
- Private serialized fields use `_camelCase` with `[SerializeField] private`, grouped with `[Header(...)]`.
- Player scripts read devices directly (`Keyboard.current`, `Mouse.current`) and null-check them in `Update`; the `InputSystem_Actions.inputactions` asset exists but is not yet wired up.
- Data types like `WaterFlowData` are immutable `readonly struct`s that clamp invalid (negative) values in the constructor, with units documented in XML comments.
